# Development guide

Everything you need to build, test and run Skip Launcher. For *what* the code does, read [architecture.md](architecture.md); for adding a
game, [adding-a-game.md](adding-a-game.md).

## Setup

You need **Node.js 20+**, **pnpm 9+** and **Python 3.9+**. The backend uses only Python's standard library (the Deck has no pip), so there is nothing to install for it.

```bash
git clone https://github.com/evertonfxavier/skip-launcher.git
cd skip-launcher
pnpm install
```

## Everyday commands

| Command | What it does |
|---------|--------------|
| `python3 -W error::ResourceWarning -m unittest discover -s tests` | All backend tests (under a second). They never need game files. `-W error::ResourceWarning` makes unclosed files fail. |
| `pnpm test` | The same, through pnpm |
| `pnpm run test:ui` | Pure UI logic (for example which game the panel shows) with node's built-in runner, no extra dependency |
| `npx tsc --noEmit -p .` | Type-check the UI |
| `pnpm run build` | Build the UI into `dist/` |
| `pnpm run build:zip` | Build `out/skip-launcher-vX.Y.Z.zip` (the file users install) |
| `pnpm run brand` | Re-render the logo and the social preview from `assets/logo.svg` |
| `python3 tools/gen_supported_games.py` | Refresh `SUPPORTED_GAMES.md`, the one place that lists the games (a test fails if it is stale) |
| `python3 tools/scaffold_game.py ...` | Create the starting files of a new game ([adding-a-game.md](adding-a-game.md)) |

## Project map

| Path | What |
|------|------|
| `main.py` | Decky entry point: the callables the UI uses |
| `src/` | The React UI: game select, skip switch, settings; `src/i18n/` has the English and Brazilian Portuguese catalogs |
| `py_modules/skip_launcher/engine.py` | State, status, `set_option`, `restore` |
| `py_modules/skip_launcher/launch.py` | The launch-option text: executable swap or command-line switch |
| `py_modules/skip_launcher/steam.py` | Steam libraries, the Proton prefix, the running-game guard |
| `py_modules/skip_launcher/iniutil.py`, `regutil.py` | Edit one `.ini` or one Wine registry file, byte for byte |
| `py_modules/skip_launcher/profiles/` | One module per game, plus `base.py` |
| `assets/` | The logo and the social preview (`logo.svg` is the source) |
| `tools/` | Developer tools: `gen_supported_games.py`, `scaffold_game.py` |
| `tests/` | Synthetic-fixture tests (`tests/ui/` for the pure UI logic) |
| `docs/` | These guides, the architecture, and one page per supported game |

Files marked "Generated by … do not edit" are produced by a tool; change the tool or its input, then regenerate.

## Tests: what is covered

- **Settings files** (`test_iniutil.py`, `test_regutil.py`): byte-identical round trips, only the asked lines change, encodings, line endings, no section created.
- **Launch options** (`test_launch.py`): enabling and disabling round trips with and without the player's own options; the executable-swap text is run through `bash` to prove it rewrites only the launcher argument.
- **Engine** (`test_engine.py`, `test_max_payne.py`): status codes, exact undo, a missing or unreadable file is never created, the running-game guard (every spelling, plus the Wine prefix), atomic writes.
- **Consistency** (`test_consistency.py`): every status code and every setting has its translations, profiles make sense.
- **Tools and the repository** (`test_scaffold.py`, `test_supported_games.py`, `test_repo_health.py`, `test_ci_version.py`): the scaffold makes importable skeletons, the generated list is up to date, the community files exist, every relative link in the Markdown files works.

CI runs all of them, plus the UI tests and the type check, on every push and pull request.

## Working with a real Deck

You do not need SSH to test: build the zip (`pnpm run build:zip`), copy it to the Deck, and use **Install Plugin from ZIP** in Decky's Developer settings. With SSH you can iterate much faster and read logs.

### Turn SSH on (once)

In **Desktop Mode** open Konsole and run:

```bash
passwd                                  # set a password for the user "deck" (needed the first time)
sudo systemctl enable --now sshd        # start the SSH server now and on every boot
ip -4 addr show | grep inet             # find the Deck's address (Wi-Fi is usually wlan0)
```

Then from your computer: `ssh deck@<address>`. If you get *Connection refused*, SSH is off (the SteamOS default): repeat the steps above. A SteamOS update may switch it off again.

### Safe habits

- **Analyse on your computer.** Copy files with `scp deck@<address>:<path> ./work/`; do not edit game folders by hand.
- **Look before you install.** Copy the zip to the Deck's `/tmp`, unzip it there, and from `py_modules` run `Engine(...).get_game("<appid>")` against the real library with a temporary settings folder: it only reads.
- **Close the game first.** The plugin refuses to write while a game runs, but a test is easier without one.
- **Logs:** `~/homebrew/logs/Skip Launcher/` and `journalctl -u plugin_loader`.
- **The launch option lives in Steam's memory.** To read or set it from a script, the plugin's own code is the model: `SteamClient.Apps.RegisterForAppDetails` and `SetAppLaunchOptions` in `src/lib/steam.ts`.

## Releases

Releases are automatic: **every push to `main` is released**, so the release never lags behind the code. CI runs the tests, builds the zip and publishes it as `vX.Y.Z` (with a `.sha256` and generated notes). The version is decided by `scripts/ci_version.py`:

- `package.json` carries a version that has no release yet (you bumped it by hand, for example for a new minor): that version is released as is.
- Its release already exists at another commit: CI bumps the **patch** (0.2.1 to 0.2.2, the next free one), moves what is under `## [Unreleased]` in [CHANGELOG.md](../CHANGELOG.md) to `## [0.2.2] - date`, builds the zip with that version, commits `chore(release): v0.2.2 [skip ci]` to `main` and publishes the release at that commit.
- A re-run of the commit that was already released does nothing. A pre-release (`X.Y.Z-beta.1`) is never bumped automatically. Pull requests build and test but never release.

Things to know:

- The bot adds a commit to `main` after each release: **`git pull --rebase` before your next push**.
- If `main` moves while a release run is going, the bot's push is refused and that run fails without publishing; the run of the newer commit releases both.
- Pick the version yourself ([semantic versioning](https://semver.org)) when it is more than a patch: minor for a new game or feature, major for breaking changes. Put the line in `## [Unreleased]` of the changelog in the same pull request.
- Contributors normally **do not bump the version**.

## Conventions

- Code, identifiers and docs are in English. UI text lives in `src/i18n/en.json` (the source) with `pt-BR.json` beside it: add a key to both (`tests/test_consistency.py` fails on a missing key or a different `{placeholder}` set), use `t("key", {name})`, and keep proper names as they are. A new status the engine reports gets a `code` in `engine.py`, an entry in `status_codes.py` and a `code.<code>` key in the catalogs.
- Module docstrings explain *why* (format facts, the failure a rule prevents), not what the next line does.
- Small, focused commits; messages in the imperative (`Add Some Game profile`). The pull-request template lists what reviewers check.
